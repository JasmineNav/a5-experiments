# 11-08 SH 材料可行性 pilot

## 范围与隔离

依据张雨欣《A5 SH实验任务调整——pilot版》，原始导出存于 `docs/A5-SH-1108-pilot原稿.md`，反馈候选截图为 `docs/A5-SH-1108反馈候选.png`。

这是一个**独立实验入口**，不是替换原正式 SH：保留现有 `npm start`、正式预分配、SH05、SL、眼镜适配器与交互启动器不变。这个入口不实例化眼镜适配器，不发送任何消息，不生成任何真实呈现证据。当前完成度反馈显示在**电脑端界面3**，不是眼镜端叠加内容。本轮只测试材料与反馈的负荷差异；不能宣称已验证 OST 可读性或心理负荷确实下降。

新入口复用 `@a5/desktop/clock.ts` 的 `Clock/systemClock` 和 `Store` 的事务、乐观锁、`stateLog/event/acceptCommand` API。公共 `Store/Session` 仅增加有默认类型的泛型参数，正式 SH/SL 行为不变。pilot 使用自己的状态机、材料快照和独立 SQLite 文件。只追加状态历史和事件随日志导出；没有干预发送，intervention_history 应为空。

## 启动

要求 Node.js **24+**，原生 TypeScript，仓库无编译构建步骤。在仓库根目录执行：

```sh
npm ci
npm run start:pilot --workspace=f5-sh-pilot
```

打开 `http://127.0.0.1:5173/pilot`（`/admin`、`/` 是同一入口）。先由主试配置并输入被试编号，再把页面交给被试。服务仅监听 `127.0.0.1`；不支持其他电脑或眼镜浏览器远程访问，勿通过代理公开。它是受信任本机环境用工具，不提供账户级权限隔离；CSRF token 是跨站保护，不是身份认证。

与原正式 SH 服务端口相同，不能同时占用。需要并行时：

```sh
PORT=5175 npm run start:pilot --workspace=f5-sh-pilot
```

原正式 SH：`npm run start --workspace=f5-sh-pilot`，5173；SL：`npm run start --workspace=f5-sl-pilot`，5174。原 `.bat/.command` 交互启动器仍启动原实验，不启动这个独立 pilot。

Windows PowerShell（先确认 `node --version` 为24+）：

```powershell
$env:PORT="5175"
$env:A5_PILOT_FEEDBACK="progress"
$env:A5_PILOT_ORDER="feedback-first"
npm run start:pilot --workspace=f5-sh-pilot
```

不要同时开两个 pilot 服务操作同一个数据库。重复被试编号不能新建，须在已有会话列表恢复；重测用新编号。浏览器刷新会从服务器保存的页面/输入继续。电脑端输入串行持久化；请求丢失响应时使用相同命令编号重试。网络错误会显示重试按钮；不要在有待保存输入时刷新。多个作答窗口的旧页面操作被拒绝，应保留单窗口。

## 配置与平衡

主试首页可以逐会话设置以下项目。创建会话后配置及材料固定，不受后续配置修改影响。

| 环境变量 | 值 | 默认 |
| --- | --- | --- |
| `PORT` | 1—65535 | `5173` |
| `A5_PILOT_FEEDBACK` | `progress` / `registered` / `message` | `progress` |
| `A5_PILOT_ORDER` | `no-feedback-first` / `feedback-first` | 按被试编号 |
| `A5_PILOT_SOURCE` | `participant` / `standard` | `participant` |
| `A5_PILOT_PRACTICE_SCALES` | `true` / `false` | `false` |
| `A5_PILOT_PRACTICE_FEEDBACK` | `true` / `false` | `false` |
| `A5_PILOT_RUNTIME_DIR` | 独立数据目录 | `f5-sh-pilot/runtime/pilot-1108` |

环境变量作为首页默认值；主试可在首页覆盖后建会话。编号末尾数字用于四人平衡：P01/P02先无反馈，P03/P04先有反馈；P05起循环。无数字后缀时必须显式指定顺序。仅提供分配规则，不强制研究招募人数；主试应实际安排每顺序各两人。数据套始终与反馈条件绑定，调换顺序不会对调材料：无反馈使用 B/D 合格那套，有反馈使用 B/C 合格那套。因此本轮的反馈效应仍可能混有材料差异；如需材料×反馈完全交叉须另行确认。

## 流程与默认解释

1. **练习：展台 A—D 四方案**。按表格和答案处理，纠正文稿中只写 A/B/C 的笔误。默认无反馈、无量表。
2. 两个正式 SH01 任务，顺序按配置。
3. 每任务：界面1读要求（含情景）→界面2算费用/多选方案→阶段一量表→界面3照着结果填写→阶段二量表。练习默认跳过两份量表。
4. 计算页可以返回要求页；草稿与首次计算页打开时间保留，返回不重置时钟。
5. 阶段一量表3项：心理需求、信息整合需求、需要付出的努力；阶段二另加放松感，共4项。所有题1—7必答，不预选。放松感原题只问“记录最终答案”，故不在阶段一提问。
6. 界面3默认显示**被试自己刚才的输入**，包括错误答案；`source=standard` 可改为文档标准答案。不会向被试显示对错。每个费用最多两位小数，合格方案编号如 `B、D`；格式完整但错误的答案照常提交。
7. 有反馈仅在界面3生效；每个非空字段算一项（合格方案编号1项、A—D费用4项，共5项）。输入即更新，不要求另点逐项提交。修改保持登记，清空即回退；这不是正确性/格式判定。不用颜色或文字提示“答对”。无反馈条件没有进度条、标绿、完成文字，也不显示逐项“已保存”，避免额外完成反馈污染。
8. 结束页提供访谈提纲，主试自行记录访谈；程序不录音。

## 三种反馈形式与推荐

- **`progress`（默认）**：静态5格分段条＋“已登记 X/5项”。清楚说明剩余量，文字少，不重复答案，最符合降低“还有多少没做”不确定性的目的。缺点是缺乏逐项定位、可能带来赶进度感；只反映非空而非最终正确。
- **`registered`**：登记列表更新原始输入，已登记项标绿并加勾（不只靠颜色）。定位清晰、便于确认哪些结果已记下；但额外重复答案和绿色可能增加视觉负担，并被误解为答对。所有形式都明确“仅表示已填写，不表示答案正确”。
- **`message`**：下方列出“某某结果已完成”，清空即移除。语义直白；但逐项文字更新会增加阅读和视线移动，空间占用也随完成项变化。

**推荐先用静态分段条**，待 ChRonic 拍板。若未来放到 OST 眼镜上，标绿须验证真实背景对比度与色辨能力；长文字更容易遮挡现实视野，进度条应固定位置、小面积、无动画无声音。本实现没有验证这些真机效果，不应据此宣称能使被试放松。

## 时间、候选事件与判分

- 时间间隔统一取公共 `Clock.mono`，不以墙钟差计时；事件另记 `timestamp_iso/server_received_at`（ISO UTC，分析显示时转 Asia/Taipei）。`elapsed_ms` 为会话开始以来毫秒。
- **第一步用时**：要求页开始至计算页“下一步”，包括读要求、计算、返回要求的时间；另导出 `compute_from_first_open_ms` 便于只看计算页首次打开之后。
- **第二步用时**：阶段一量表提交后打开誊写页至最终结果提交；不含量表。
- **总操作用时**：两步之和；另有 `task_wall_elapsed_ms`，包括中间阶段一量表，不含阶段二量表。只把完成的阶段计分/计时；未完成字段为 null。
- **T0行为候选**：计算页 A 已是有效非负数字（不要求算对）之后，首次接收 B 的非空输入；记录 `t0_behavioral_candidate`、输入证据和服务端单调时间。它只代理“可能正算B”，不能证明实际认知状态；输入频率与网络延迟可能影响时间。未发生则保持 null，不伪造。
- **T0次级标记**：计算页首次打开后20秒，记录 `t0_20s_secondary`；候选毫秒按精确阈值计算，观察毫秒按服务端实际检查记录，二者分开。离开阶段或快速做完时仍会记录，并标记当时页面/已结束；不能误当成仍在高负荷阶段。
- **T1/T2**：计算“下一步”和誊写B首次非空输入，各记候选事件，仅日志，无任何消息呈现。
- 服务端每秒检查20秒标记和持久化计时。浏览器刷新不重置时钟；服务器重启从最近检查点续接，**停机时间不计入**，有 `server_restarted/timing_discontinuity` 证据，可能损失最后不足1秒的未检查计时。重启会话不应当作连续计时样本，建议重测并保留原日志。
- JSON导出包含：材料/配置快照、两阶段原始输入、实际誊写来源、标准答案（在 phase1_submitted 日志）、阶段量表、阶段/总用时、T0/T1/T2、只追加事件及状态历史。标准答案与判分不进入作答 API 公开视图。
- 分开导出：第一阶段相对标准答案正确率；誊写相对标准答案的正确率；誊写相对所见来源的复制正确率。每阶段5项（费用各1项、合格编号集合1项），方案顺序/分隔符不影响得分。默认不把“忠实复制自己的错误”算作客观答对。
- 完成度事件记录的是服务器接受后的状态，不是浏览器可见回执或眼镜出光证据。真实暂停/休息控制尚不支持；页面闲置计入所在阶段。访谈不写数据库，实验员另行记录。

## 验证

```sh
npm run check
node --test f5-sh-pilot/tests/pilot1108.test.ts
node --check f5-sh-pilot/public/pilot1108/pilot.js
```

仓库使用 Node 原生 TypeScript，无 `build` 脚本，`typecheck + test + doctor` 为现有检查方式。本轮新增覆盖：三套材料、两个顺序、三种反馈纯HTML、清空回退、阶段流程、量表、源答案切换、各类时刻/用时、时钟回拨、幂等重试、状态乐观锁、只追加日志、重启和 HTTP。

**尚需现场验收**：真实浏览器完整操作与窄屏布局、下载/刷新交互、Windows PowerShell/原启动器、真实显示设备及色彩对比、被试的实际高低负荷差异。自动化渲染函数测试不等于浏览器视觉验收。

## 需向雨欣确认（当前不阻塞实现）

1. 练习是否确实是A—D四方案？本版按表格采用四个。
2. 誊写页用被试原答案还是标准答案？本版默认原答案，可切换且两套都记日志。
3. 量表是否每阶段立即填，还是任务后回顾两阶段？本版立即填写；中间量表可能影响第二阶段的放松感，需要确认。
4. 第一阶段要不要另设计放松感题干？本版只在第二阶段询问放松感。
5. T0采用20秒规则还是A算完后的行为代理？本版两者独立记录，以行为代理为主，不发信息。
6. 是否确认本轮不验证消息打断？本版只记录候选时刻，后续pilot再验证真正触发。
7. 练习是否也要量表与反馈？本版默认都关闭，分别可开。
8. 完成反馈在非空输入时更新是否足够，还是需要逐项确认按钮/失焦才算完成？本版输入即更新，清空回退。
9. 三种反馈最终选哪一个，显示在电脑还是眼镜？本版默认电脑端静态分段条；未实现眼镜端完成度叠加。
10. 是否需要两套材料×有无反馈完全交叉平衡？本版遵照文稿固定材料-条件配对，只平衡顺序。
11. 正确率是否采用本版每阶段5项等权评分？是否需要再细分合格方案多选的逐选项评分？

12. 第一阶段时长是否应包含读要求？本版包含读要求，另提供从计算页首次打开计时供对照。
